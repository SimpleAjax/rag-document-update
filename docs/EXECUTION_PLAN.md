# Execution plan: local ADK chatbot with Codex CLI and RAG

**Project:** `rag-document-update`
**Phases:** 1 and 2 complete
**Status:** Phase 1 and Phase 2 implementation and local validation complete. Phase 2 uses an isolated project-local PostgreSQL 18 cluster on `127.0.0.1:55433`.

## Phase goal

Build a small local chatbot using Google ADK. ADK owns the chat session and agent loop. A narrow custom model adapter calls the signed-in Codex CLI to generate each answer. The user can send several messages in one conversation and see the assistant reply through a local development chat interface.

Phase 1 established the agent runtime and its connection to Codex. Phase 2 adds a small RAG path using project-owned Markdown sources, local embeddings, and PostgreSQL.

## Integration decision

ADK Python has model connectors, including LiteLLM, but Codex CLI is not a built-in ADK model provider. `codex exec` is a command-line agent interface. For this phase, implement a small ADK `BaseLlm` adapter that sends the ADK conversation messages to `codex exec` and returns its final assistant message as the model response.

The adapter must call the installed `codex` executable as a subprocess and rely on the user's existing Codex CLI sign-in. It must not read, copy, or log the Codex auth file or access tokens. No `OPENAI_API_KEY`, `CODEX_API_KEY`, or Gemini key is needed. Generation uses the signed-in Codex account and needs network access.

Use JSONL output so the adapter can identify the final agent message and the turn's completion or failure. Start each generation call as an ephemeral, read-only run in an empty local working directory. Pass the ADK conversation history on each call so multi-turn context does not depend on Codex retaining a separate transcript. Keep the working directory and Codex configuration local to the project; do not modify the user's global Codex configuration.

This adapter is a prototype seam, not an official ADK-to-Codex provider. If the current CLI cannot run this way with saved sign-in, stop at the integration spike and report the specific blocker before adding fallback model credentials.

## Phase 1 scope (complete)

- Python 3.12 and `uv` for the local environment.
- Google ADK Python with one `LlmAgent`, one instruction file, `Runner`, and in-memory sessions.
- A custom text-only ADK model adapter around `codex exec`.
- ADK's local development chat interface for manual conversation tests. Add a custom UI only if the ADK interface cannot exercise the required conversation flow.
- One small local test conversation and minimal run/error logging. Do not persist chat content beyond the local ADK development session.

No Postgres, Docker, embeddings, ingestion, document search, MCP data tools, customer data, prompt-injection experiments, or production deployment in this phase.

# Phase 2 execution plan: first local RAG slice

## Goal

Add one end-to-end retrieval path to the working chatbot. Keep policy source files editable in the project. Ingest one fictional returns policy, show ingestion progress, retrieve relevant passages through one read-only ADK tool, and answer with document/version/passage citations. Re-ingest a later policy version and confirm the new active version is returned.

## Stack and boundaries

- Keep Python 3.12, `uv`, Google ADK, and the signed-in Codex CLI adapter from Phase 1.
- Use the local PostgreSQL installation and a project-isolated database/schema. Do not use Docker.
- Use `psycopg` for PostgreSQL access and SQL migrations kept in the project.
- Use FastEmbed with `BAAI/bge-small-en-v1.5` (384 dimensions) for local query and document embeddings. Cache model files under ignored `.local/`.
- Keep source Markdown files in `data/policies/`; files are the editable source of truth. Store source hash, document/version metadata, ingestion job/events, active-version state, passages, and embeddings in PostgreSQL.
- Use a synchronous local ingestion command for this small corpus. Record each state transition and a safe error. Do not add a separate worker or queue in this phase.
- Extend the text-only Codex adapter with a constrained JSON action response so it can emit one function call declared by ADK. Keep Codex's own shell, apps, and subagents disabled; ADK executes only its registered read-only `search_documents` function.
- Retrieve only active, ready passages and return passage IDs, document IDs, versions, and scores with the text.
- Show ingestion job progress in the CLI and retrieval tool arguments/results in ADK's local development trace. Answers cite the returned document/version/passage IDs.
- Use synthetic policy text only. Do not add role-based access control, user authentication, prompt-injection experiments, production deployment, or other policy documents in Phase 2. Those need separate acceptance criteria.

## Database target safety gate

The earlier project requirements explicitly prohibit using the Perfastra PostgreSQL database on port `55432` and specify a project-isolated PostgreSQL 18 target on `127.0.0.1:55433`. Current inspection found the existing listener on `55432`, with its data directory under the Perfastra project. A new cluster is initialized under ignored `.local/postgres-data`, bound to loopback on `55433`, and uses SCRAM password authentication. The project database is `rag_document_update`; credentials are in ignored `.env`. The Perfastra listener and data directory were not changed.

### Task 1 — Safe PostgreSQL preflight and connection settings

- Confirm a project-isolated local PostgreSQL target and its port/database. Keep credentials in an ignored local `.env`; never print them or commit them.
- Add a small connection helper that validates the server/database identity before writes and uses parameterized SQL.

### Task 2 — Minimal schema and source fixture

- Add the synthetic `RETURNS` v1 Markdown source with stable ID/version metadata.
- Add migrations for documents, document versions, ingestion jobs/events, passages, and active-version state. Store embeddings as fixed-length numeric arrays for this small corpus; do not require pgvector.
- Make migration application explicit and repeatable; never drop existing schemas or data.
- Validate a fresh project database can migrate and that a repeated migration is safe.

### Task 3 — Ingestion command and progress tracking

- Parse and validate front matter, compute a source SHA-256, split the policy into deterministic passages, generate local embeddings, and write the version/passages transactionally.
- Record states `PENDING`, `VALIDATING`, `CHUNKING`, `EMBEDDING`, `INDEXING`, and `READY`, plus ordered job events and safe failure details.
- Treat same-version/same-hash ingestion as idempotent. Reject changed content under an existing version. Activate a new version only after all its passages are ready.
- Validate the job trail, row counts, idempotency, changed-content rejection, and retry after a simulated embedding failure.

### Task 4 — Read-only semantic search tool

- Embed each query locally, select only passages belonging to active ready versions, calculate cosine similarity in Python, and return the top five passages with stable citations.
- Register one read-only `search_documents` tool with the ADK agent. Require a search for policy questions and answer only from returned passages; abstain when retrieval has no relevant support.
- Validate the adapter-to-ADK function call and result cycle with a local stub before enabling the live retriever.
- Validate direct retrieval for the 30-day returns policy, an absent fact, and a later 14-day version. Confirm the old version is not returned after activation.

### Task 5 — Visible local acceptance

- Use the ADK local chat UI to run a grounded returns question and a follow-up. Inspect the tool call/result in the trace and verify the answer citation matches a returned passage.
- Ingest the 14-day update and repeat the question; capture job events, active version, passage IDs, answer, and citations.
- Confirm chat sessions remain in memory, secrets and model files are ignored, no database credentials enter tracked files, and the local app/server can be stopped cleanly.
- Update the README with exact local setup, migration, ingestion, run, and stop commands. Record versions and evidence. Complete the Phase 2 acceptance summary before starting any later hardening phase.

## Phase 2 completion gate

Phase 2 is complete when the project-isolated PostgreSQL target migrates, the source policy ingests with a visible job trail, the chatbot answers from an active returned passage with a matching citation, and a new policy version becomes active only after successful ingestion. No role-access or prompt-injection security claim is part of this phase.
